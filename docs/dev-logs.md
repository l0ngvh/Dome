# Dev logs
- Terminal in remote box should be managed as windows by Dome. Wezterm does this well, but all its windows are closed on disconnect, and it's hard to have Dome memorize Wezterm windows position.
- Maintaining those status bars integration seems to be as much work as building a status bar ourselves.
- TOML is showing its limitation. Modeling $mod1 $mod2 pattern is awkward, platform specific configuration requires putting [macos] and [windows] on almost every key.
- The disadvantage of moving windows off screen is that all offscreen windows participate in the global z order stack. When the last window of a workspace closes, Windows focuses the window next in the z order, which is an offscreen window belong to the other workspace, causing them and their workspace to be brought forward.
- All Windows' windows are enclosed by an unadjustable margin, so we need to account for them while tiling the windows to avoid leaving gaps, by enlarging the windows by the margin amount. This, however, can cause the window to spill over the next monitor when placed at monitor's edge. This should be benign since only the invisible margin would spill over, unless when it's a DPI unaware window.
- When a DPI unaware window (like Winrar or TK windows) is controlled by a DPI aware application (Dome), all those Get/SetWindowPos are scaled by Windows first based on the monitor DPI. For some reasons, Windows's approach to scale DPI unaware window, when the window spans multiple monitor is, to scale down each edge coordinate based on the scale of the monitor the edge is on, then scale up again based on one single monitor where most of the window is in. So when the 2 monitors differ in DPI (like my cheap reused monitors setup), when a few pixels (belonging to the invisible margin) of a window spilled to a lower DPI monitor, the entire window is stretched by the ratio between monitors DPI.
- Steam draws its own title bar, so its set its window style as WS_POPUP and no frame. We currently ignore all WS_POPUP and no frame windows, so now we have another branch to detect whether this window is a parent window (through GW_OWNER). Borderless fullscreen games also use this style, but it seems some of them don't declare themselves parent window (perhaps because they are launched from a launcher?), and we have to rely on the window covering the whole screen to detect them.
- Moving all child windows with their parent when their parent moved is going to bite us one day.
- On mac, moving windows to another monitor the first time will cause mac to snap that window size based on the last monitor size. And this messes up our constraint detection on macOS, since there is no API we can use to get the size constraint, and Dome has to rely on where the window end up after a move to learn that.
- Plugging/unplugging monitor on macOS causes all windows to be moved randomly, maybe because there are more spaces available now, or because some windows remember their position when a certain monitor is present. We have to disable our detection when this happens.
- Turned out AttachInputThread doesn't grant foreground window privilege if it's called from a background thread. And if it's called from Dome's thread, if the attached thread hangs, Dome is cooked.
- Somehow CGEventTap can live on a background thread
